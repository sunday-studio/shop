# Backend status (handoff)

_Last updated 2026-10-12._ Read this first if you're picking up the server side. The detailed spec and milestone checklists are in [PLAN.md](PLAN.md).

## What it is

A Go server (`api/`) with SQLite, an OCR sidecar (`ocr/`, Python + PaddleOCR) and Docker Compose (`deploy/`). It serves the REST API (`/v1`, contract in [`openapi.yaml`](../openapi.yaml) **0.16.0**; migrations `00001`-`00019`), MCP for an AI assistant (`/mcp`), and the iOS app. Everything runs CPU-only in Docker, with no macOS dependency (a deliberate decision).

## Run it

```bash
cp deploy/.env.example deploy/.env    # add LOGO_DEV_TOKEN (logo.dev pk_…), optional
make setup                            # build + start; prints the app pairing password once
make test                             # Go tests (all green at the time of writing)
make e2e                              # whole-loop test in an isolated docker stack (see "End-to-end test" below)
make token NAME=assistant             # bearer token for MCP/scripts
```

- The API is at `http://localhost:8080`; `GET /healthz` shows each dependency, with no auth.
- The app pairs with URL + password (`POST /v1/auth/pair`).
- Operations (backups, optional off-site copy, remote access, upgrades): [operations.md](operations.md). Restore: [restore.md](restore.md). MCP: [mcp.md](mcp.md).

## End-to-end test

`make e2e` starts a separate Docker stack, drives it over HTTP the way the iOS app does, prints a pass/fail table and exits non-zero on any failure. It always tears the stack down, also after a failure or Ctrl-C.

- **Isolation:** compose project `shop-e2e` (`deploy/docker-compose.e2e.yml` on top of `deploy/docker-compose.yml`), API on `127.0.0.1:18480`, its own API image tag (`shop-e2e-api`), a throwaway data volume, a throwaway tmpfs for backups. The live stack (project `shop`, port 8080, volume `shop_shop-data`) is never touched, and the test refuses to run any compose command for another project (both override files also set `name:`, and `api/internal/composeguard` fails `go test` if a harness calls compose outside its guarded wrapper). The OCR container uses the existing `shop-ocr:ppocrv5` image (built once by `make e2e` if missing).
- **Needs:** Docker running, a free port 18480, and Go. About 1 to 2 minutes with a warm image cache.
- **Covers:** pairing (password set with the `shop` CLI inside the container, wrong password, device token), uploading a rendered receipt photo (real OCR, nothing mocked; dedupe 409, wrong type 415), status, lines, date and totals (printed total equals parsed sum), re-parse, shop suggestion and accept, list items with idempotent `client_id`, confirm (auto-created products and list auto-check), undo of the list checks, barcode create, the review queue and accepting a card, product merge and undo, groups and checklists (create, repeat, items, move, template, instantiate, delete, restore, `since_rev` feed), `GET /v1/list/plan` on thin data (`not_enough_data`) and its settings, categories (CRUD, delete with `move_to`), a backup run and the backup health check.
- **Open Food Facts** is external, so the API is pointed at a fake server on the host (`OFF_BASE_URL`, default empty = the real service) that answers found, not found and down. The real service is never contacted.
- **Private receipt photos:** if `spike/data/` (or `spike/receipts/`, or the folder in `E2E_PHOTOS`) holds JPEGs, they are uploaded too and the known-good ones (IMG_1463 to IMG_1474) must reconcile with the printed total; IMG_1475 is the documented curled photo and is only reported. Without photos this step is skipped and says so in the table.
- **Not covered:** no export endpoint exists (the backup status is checked through `/healthz`); the cheapest-store plan with real savings (`split`) needs receipts from two shops with the same product, which one rendered receipt cannot give, and is covered by the unit tests; the nightly schedule firing; backups to a real NAS or cloud destination; the iOS app.

## Conventions that matter

- Money is integer cents. Time is stored as UTC `2006-01-02T15:04:05Z`; local time is Europe/Amsterdam.
- `openapi.yaml` is the contract. Edit it first, then run `make gen` (sqlc + oapi-codegen). Never hand-edit `*.gen.go` or `internal/store/db`.
- sqlc on SQLite can't bind args in `ORDER BY` or mix `sqlc.slice` with named args. Use separate queries, or hand-written SQL (see `internal/search`).
- Migrations are append-only (`internal/migrations/000NN_*.sql`). The server snapshots the DB before applying new ones.
- No LLMs or embeddings: models are for OCR only. Everything must run in Docker on any CPU.
- All docs live in `docs/`. Commit per milestone. Secrets go in `deploy/.env` (git-ignored), never in commits.

## M11: what is done

- **Parser** (12 of the 13 spike receipts reconcile, sum == printed total): SUBTOTAAL / "N Artikelen" / "Van x voor y" / lone-price / savings-summary rows are ignored; a lost comma ("20015") or trailing junk ("2,49 49") is repaired only when that makes the sum equal the printed total exactly. Receipts 1 and 2 on the real DB were force-reparsed (their doubled sums are fixed: 8468 and 9980).
- **Uploads:** `shop_id` is optional on `POST /v1/receipts` (receipts show as Unassigned; they count in spend under an "Unassigned" bucket) and `photo_taken_at` is an optional hint that is never the purchase date. HEIC/HEIF get an explicit 415 (the app converts to JPEG); `purchased_at` is the client override or the date parsed from the receipt, else NULL. Never the upload time or EXIF.
- **Shop suggestions** (openapi 0.10+): `GET /v1/receipts/{id}/shop-suggestion`, `POST .../accept` (existing `shop_id` or editable `name`/`branch`/`domain`; `apply_to_waiting` moves the other unconfirmed receipts of the same branch, unassigned ones included), `POST .../reject`; also embedded as `shop_suggestion` in `GET /v1/receipts/{id}`. 7 AH + 4 Dirk headers detected, the 2 butcher slips return none.
- **Auto products** (spec: [PRODUCT-AUTOPOPULATE.md](PRODUCT-AUTOPOPULATE.md)): live, `AUTO_PRODUCTS` defaults to `on` (set `off` in `deploy/.env` to disable). Confirming a receipt links or creates products. Tested on the 13 real receipts (99 item lines: 28 links, 68 products, 5 near matches queued, weight and totals rows never become products; the category rules reproduce 50 correct / 1 wrong / 16 no hit); merge+undo, discard+undo and split+undo restore every row exactly; barcode create is tested against a fake Open Food Facts server.
- **What the backfill did on the real DB (2026-10-10):** snapshot `shop-20261010-205648.db` first. Receipts 1 and 2 were force-reparsed (a forced reparse clears `confirmed_at`, so they were confirmed again) and the confirm created 25 products and 3 links (receipt 1: 13 created; receipt 2: 12 created, 3 linked); the backfill with `skip_receipt_ids [3]` then found nothing left to do. 11 products wait in the review queue (near_match 2, no_category 6, odd_name 3). Products carry `created_via=receipt`.
- **Differences from the spec:** (1) the confirm hook runs right after the confirm in its own transaction, not the same one; a failure only sets `auto_products.error`. (2) Backfill progress is a JSON value in `settings` (`autopop_backfill_state`), not the job payload; a dry run is one rolled-back transaction; the request takes an optional `skip_receipt_ids`. (3) No `Idempotency-Key` header. (4) Matching ignores the matcher's same-shop alias bonus (+0.05): with it a 0.874 near match became a 0.924 auto-link. (5) `product_merges.into_product_id` is nullable (discard has no survivor) and has extra columns `alias_rows`, `from_review_before`. (6) Undo answers 409 for both already-undone and older than 30 days. (7) New endpoints use 422 for "cannot do that", 400 for a malformed barcode. (8) `suggested_merge` is filled on single-product, queue, review, undo and barcode responses, not in `GET /v1/products` lists. (9) After merging a `barcode_name_match` card, the surviving barcode product is re-queued as `no_category` if it still has no category.
- **Duplicate-receipt warning** (openapi 0.17, migration 00020): `possible_duplicate_of` on the single-receipt GET and on list rows of the NEWER receipt, computed on read (not stored): both parsed, same printed total, same Europe/Amsterdam purchase day, same shop or one unassigned; under 10 euro also 3 item lines on both or a line overlap. `match` is `total+date+lines` when at least 60% of the normalised item lines are shared (shared / the longer list), else `total+date`; several candidates: lines first, then equal time, then oldest. Receipts without date or total are never flagged. `POST` / `DELETE /v1/receipts/{id}/duplicate/keep` remember and undo "Keep both" (idempotent). `GET /v1/receipts/counts` gains `possible_duplicates`. Nothing is ever deleted automatically; deleting the newer receipt reverts its own list checks only. No soft delete / restore for receipts.

## Backups, off-site copy and the restore drill

- **Local first:** the `backup` service writes snapshots plus an append-only image mirror into `SHOP_BACKUP_DIR` (any folder or mounted drive, default `backups/`). That is the base mechanism and needs nothing else.
- **Optional off-site copy:** compose profile `offsite` (`make offsite-up`) runs `deploy/offsite/offsite.sh` in the `rclone/rclone` image. It copies images, then snapshots, then `last_backup.json` to `OFFSITE_REMOTE` after every successful backup, retries 30 minutes after a failure, and checks snapshot sizes at the destination. Any rclone destination works; configuration is only environment variables (`deploy/offsite/offsite.env`) or a mounted `rclone.conf`. Encrypting with an rclone `crypt` remote is recommended for any cloud destination. Without `OFFSITE_REMOTE` nothing changes.
- **Health:** the script writes `offsite_status.json` into the data volume. `/healthz` folds it into the existing `backup` check (`internal/backup/offsite.go`, `internal/httpapi/server.go`): failed or no success for 36 hours makes it unhealthy, and the detail shows the label you chose, never connection details. No new check name, so clients that read `checks.backup` see it.
- **Restore from off-site:** `offsite pull` (`make offsite-pull`) brings the copy back into the backup folder (it fails if no snapshot arrives), then the normal `restore` runs. See restore.md.
- **Restore drill:** `make restore-drill` (`api/drill`, build tag `drill`, `deploy/docker-compose.drill.yml`). Project `shop-drill` only (own image tag `shop-drill-api`), port 18481, throwaway volumes. Creates data, backs up, wipes the data volume, restores, compares counts and receipt image hashes; then copies to an encrypted rclone crypt remote (a throwaway folder), loses the data volume and the backup folder, pulls back, restores and compares again. Prints PASS or FAIL per step, exits non-zero on failure. Does not use OCR.
- **Remote access:** documented in operations.md (Tailscale, any VPN, Cloudflare Tunnel, Caddy); optional example overrides without secrets in `deploy/remote/`. They were checked with `docker compose config` and the Caddyfile with `caddy validate`; none was run against a real tunnel, tailnet or domain.
- **Not tested:** a real cloud destination (S3, B2, SFTP, WebDAV, Drive, Dropbox), a real NAS mount, and the compose service running on its own schedule for a night. The script is tested with a fake rclone in `internal/backup`, and with real rclone (local and crypt remotes) in the drill. The server's pairing lockout uses the connection address, so behind a proxy or tunnel all phones share one lockout.

## Households: the tenant seam and the isolation test (openapi 0.18)

- **What it is:** every request resolves a household (tenant) from its bearer token, and the household's own service graph answers it. Self-hosting is the single-tenant case (`tenancy.Single`, one database, same pairing flow, same behaviour). The same code can serve many households with one SQLite file and one image folder each (`tenancy.Multi`). The hosted accounts, billing and sign-in are not part of this: they plug in behind two small interfaces.
- **Packages:** `internal/tenancy` (Tenant, Provider, Resolver, Directory; single and multi providers; `OpenDB` snapshots then migrates), `internal/tenantapp` (builds one household's services, the HTTP gateway, the fair job scheduler, per-household backup and export), `internal/httpapi/gateway.go` (token → household → that household's `Server`), `internal/jobs/fair.go`. `cmd/shop serve` runs through the same gateway with the single provider and keeps `jobs.Queue.Run` as before.
- **Multi provider:** `Provision` creates a household, `Acquire` opens it lazily (migrations on open, a pre-migration snapshot, an LRU of open databases, never evicting one in use), a database that fails to open answers 503 `household_unavailable` for that household only, `Erase` waits for in-flight users and removes the folder and its backup folder. Household ids are `[a-z0-9-]`, so a folder name can never escape the data directory.
- **Control seam:** `tenancy.Directory` maps a token hash to a household id. The public repo has only `MemoryDirectory`; the hosted layer supplies one backed by its control database. Tokens themselves still live in each household's `api_tokens`.
- **Glossary:** the taught words are a `translate.Glossary` owned by the household's `english.Service` (no process-wide map any more); products, auto products and MCP use it.
- **Jobs:** one queue per household; `jobs.Fair` runs one job at a time per household and takes households in turn (round robin), woken by a hint when a household enqueues and by a 30 s sweep for retries. Single mode does not use it.
- **`GET /v1/server-info`** (public, 60 s cache): `server, version, api_level (8), mode, login_methods, pairing_enabled, min_app_build, features, limits` as in `notes/hosted-api-contract.md` section 1; single mode answers `mode: single`, `login_methods: ["pairing_password"]` (empty until a pairing password is set). `GET /v1/auth/status` is unchanged.
- **Isolation test:** `make isolation` (build tag `isolation`, `api/internal/httpapi/isolation_*_test.go`). It boots two real households in process, seeds both, then calls every operation of `openapi.yaml` and every MCP tool as household B with household A's ids and expects 404 or B's own data, checks foreign ids inside B's own requests, reuse of A's barcode, category name, photo, client id and glossary word, per-household settings and image folders, deleting one household, and that A's tables are byte-for-byte unchanged afterwards. A route in the router or the spec without a probe fails the test. A static scan lists process-wide state (database handles, run-time written package variables, locks) and service graphs built outside the tenant builder. `ISOLATION_WORLD=shared make isolation` runs the same checks on two tokens in one database and must fail (about 200 `not isolated:` lines): that is the proof the test can see a leak.
- **Not done here:** hosted accounts, billing, Apple sign-in, invites, a control database, plan gates and limits (other work packages); a public export endpoint (`tenantapp.Export` is the hook, the hosted layer decides the route and the job); a runnable multi-household server in the public binary (the overlay assembles Provider + Directory + Gateway).

## Hosted mode: the HTTP layer (openapi 0.19)

- **Binary**: `api/cmd/shop-hosted` (same module as `cmd/shop`, which stays single mode). Commands: `serve`, `migrate`, `admin ...` (`admin token create`, `grant`, `account find`, `audit tail`, `lifecycle run`), `healthcheck`, `version`. All configuration is environment (see `cmd/shop-hosted/config.go`): `SHOP_MODE=hosted`, `SHOP_ADDR`, `ADMIN_ADDR` (loopback), `ADMIN_TOKEN_HASH`, `SHOP_DATA_DIR`, `SHOP_CONTROL_DB`, `SHOP_EXPORT_DIR`, `SHOP_SEALER_KEY`, `SHOP_TRUST_PROXY`, `SHOP_LIMIT_*`, `SHOP_APPLE_*` (`api/internal/hosted/APPLE.md`), `SHOP_REMINDER_WEBHOOK_URL`, `SHOP_SMTP_*`.
- **Local run**: `make hosted-run` starts it in a throwaway folder against the in-process fake Apple (public `127.0.0.1:18495`, admin `127.0.0.1:18496`, admin token `sa_hosted_run_local`). `POST /admin/v1/dev/identity-token|transaction|notification|siwa-event` (admin auth) mint values Apple would sign, so sign-in, a trial, renewals, lapse, export and deletion can be driven by hand or by the e2e.
- **Packages**: `internal/hosted/hostedapi` (routes, middleware, views, export worker, admin API, scheduler, reminder sinks), `fakeapple`, `hostedworld` (test world), plus small hooks in `httpapi` (`WithExternalAuth`, `WithUploadGuard`, hosted-only 404s on a single server).
- **Order of checks** for household routes: token, `/mcp` refusal, plan gate (`plan_required` / `read_only`), per-token rate limit, requests in flight, upload rate, idempotency, upload guard (size, queue, month, day, storage), the household Server.
- **Tests**: `hostedapi` (every endpoint and error code with the fake clock), `cmd/shop-hosted` (the whole lifecycle over real HTTP), `make isolation` now also runs the whole isolation suite against the hosted service (two accounts, control database) plus a household member test.
- **Not done**: scheduled per-household backups, image recompression, household rename, X-Request-Id. Real Apple credentials and the production root check are the owner's (see APPLE.md). Decisions: `notes/decisions-log.md` (hosted wiring).
